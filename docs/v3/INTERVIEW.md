# 직접 재현하고 설명할 내용

## 확인된 기여

- 사용자: 지원 목적과 요구사항 제시, 결과물에 대한 피드백, GitHub 저장소 생성.
- Codex: 공개 자료 조사, 구현, 시뮬레이션 실행, 비교·실패 분석, UI/브라우저 검증, 문서화와 배포.
- 외부: MuJoCo/Three.js 라이브러리, Menagerie Panda 모델. 이 자산을 직접 제작한 것으로 기재하지 않는다.

사용자가 직접 코드를 작성·학습·튜닝·실험했다는 사실은 확인되지 않았다. 포트폴리오에 실을 때 “AI 도구를 활용해 구성한 프로젝트이며, 내가 직접 검증한 부분은 …”처럼 **실제로 수행한 범위**를 작성한다. 아래 작업은 권장 후속 실습이며 이미 수행한 사용자 성과가 아니다.

## 먼저 직접 할 3개 실습

1. `--seed 100 --condition occluded`를 두 방법으로 각각 실행한다. `camera-0.npz`를 열어 목표 픽셀이 없는 이유, `camera-1.npz`와 차이, JSON의 관측→접근 순서를 설명한다. 원본을 보존하고 `work/my-*`에 저장한다.
2. `shifted-107-feedback`의 `run.json`에서 `verify_grasp`, `retry`, 두 번째 `observe` 시점과 `ctrl`을 찾아 그래프로 그린다. 손가락 간격이 물체 존재를 완벽하게 증명하지는 못한다는 한계를 설명한다. 그립 폭 판정에 영상 검증을 추가하고 새 평가 폴더로 비교하는 코드 작업으로 확장할 수 있다.
3. **새 평가 전에** 기준을 정한 뒤, 개발 seed 10–14에서 카메라 누락 또는 depth noise 조건을 추가한다. 최종 평가 seed를 새로 분리한다. 기존 성과를 덮어쓰지 않고 성공률·평균 오차·관측 비용·실패 유형을 함께 보고한다.

## 면접에서 설명할 핵심

“한 번 관찰한 위치가 유효하지 않으면 접근이 맞아도 집기는 실패합니다. RGB-D에서 얻은 위치로 제어하고, 추가 관측으로 가림과 위치 변화를 보완했습니다. 동일한 80개 조건별 장면에서 기준 20회, 개선 60회 성공했고 범위 밖 20회는 여전히 실패했습니다.”

그 뒤 다음 질문에 답할 수 있어야 한다.

- depth와 카메라 외부 파라미터를 이용한 픽셀→월드 변환은 무엇인가? 왜 알려진 높이와 색상이 필요한가?
- `data.ctrl`과 `data.qpos`를 직접 바꾸는 것은 어떻게 다른가? IK scratch state와 실제 물리 상태는 어떻게 분리했는가?
- 집었다는 판정과 최종 놓기 성공은 어떻게 다른가? 손가락 간격만으로 어떤 오탐이 가능한가?
- 추가 카메라의 비용은 무엇인가? 개선이 재시도 때문이라고 단독 주장할 수 없는 이유는 무엇인가?
- 75%가 어떤 조건의 분모인가? 현장 성공률로 확대 해석하면 안 되는 이유는 무엇인가?
- 정답 좌표가 어디에서 사용되고 어디에는 전달되지 않는가? 정답 높이·기하 priors는 어떤 한계인가?
- Python 결과와 브라우저 결과가 다른 이유는 무엇인가? 각각 어떻게 재현하는가?

## 다음 확장에 필요한 것

- 학습: 더 많은 물체·카메라·조명·질량·마찰 변화와 train/validation/test 분리. 수집한 raw RGB-D와 관절·action을 정렬하는 dataset loader부터 직접 작성한다. 현재 기록은 자동으로 LeRobot 데이터셋 형식이 아니며 학습하지 않았다.
- ACT/SmolVLA: GPU, 충분한 시연·실패 복구 데이터, 학습 seed와 동일 조건 평가가 필요하다. 단순히 모델을 로드한 것을 성능 개선으로 보고하지 않는다.
- 시점 이동: 손목 카메라 모델·관절 가동 범위·가시성과 충돌 검사, 시점 선택 비용/효과 평가. 지금은 두 고정 카메라 선택이다.
- ROS 2: 좌표계/시간 동기화, 센서·제어 인터페이스, MoveIt 및 하드웨어 브리지와 실기 안전 검증. 현재 ROS 2 연동은 없다.
- 실제 장비: 카메라·로봇 보정, depth 품질, 접촉·힘·마찰 차이, 비상정지와 제한 속도 검증. 시뮬레이션 성공을 실기 성공으로 쓰지 않는다.
